# Config Sync — Per-Flavor Agent-Def Generator

`milknado config sync` makes milknado.toml's per-flavor config the single source
of truth for **worker identity** (tool allowlist, model, turn cap) by generating
agent-definition files that each target harness reads natively.

The primary consumer is milknado's own native Workflow path — where `agent()`
takes no `tools` parameter and the only per-flavor lever is `agentType`, which
resolves to a def file. The secondary consumer is the user directly, gaining
portable worker identities across Claude Code, opencode, and Codex.

See [[history/config-sync-decisions]] for the four ADRs behind these choices;
[[workflow-executor-decision]] for the native Workflow backend context.

## The gap this closes

On the native Workflow path, `milknado_todo_claim` computes a per-flavor `tools`
tuple and returns it in the claim payload (`src/milknado/mcp_node.py:71-92`) — but
`node-runner.js` reads only `{agentType, model, maxTurns, label}` from the payload
(`plugins/milknado/workflows/node-runner.js:104-109`). The computed `tools` are
dropped. The only honored per-flavor lever there is `agent_type` (→ def file).
`config sync` generates those def files so `agentType` resolves to the correct
per-flavor allowlist.

The subprocess ralph path already honors per-flavor tools via `--allowedTools`
(`src/milknado/domains/common/agent_argv.py:135-148`); this slice does not touch it.

## Pipeline: resolve → classify → project

For each flavor:

1. **Resolve** — `resolve_flavor_identity(cfg, flavor)` (`_identity.py:102`) calls
   `resolve_worker_tools(family, override.tools)` to get the effective tool tuple,
   then parses `--model <x>` out of the resolved `execution_agent` string (fallback:
   family default), and takes `max_turns` from the override or config default.
   Result: a frozen `FlavorIdentity(flavor, tools, model, max_turns, is_write_capable,
   user_controlled_tools)`.

2. **Classify** — `_is_write_capable(tools)` (`_identity.py:41`) determines whether
   the resolved tool list grants any write or exec capability. This single boolean
   drives the opencode and Codex projection.

3. **Project** — per-harness renderer emits the appropriate format:

| Harness | Output | Fidelity |
|---|---|---|
| Claude Code | `.claude/agents/milknado-worker-<flavor>.md` — literal `tools:` list, `model:`, `maxTurns:` | exact |
| opencode | `.opencode/agents/milknado-worker-<flavor>.md` — `permission.{edit,write,bash}` allow/deny | capability |
| Codex | `.codex/agents/milknado-worker-<flavor>.toml` — `sandbox_mode` + `developer_instructions` stub | coarse |

`danger-full-access` is never emitted. When `user_controlled_tools` is true (full-
custom `execution_agent` with no `tools` override), the CC def omits the `tools:`
line entirely — the user took full control.

## Crust (public API)

`src/milknado/domains/config_sync/__init__.py` exports:

- `FlavorIdentity` — frozen dataclass: resolved per-flavor identity.
- `RenderedDef` — frozen dataclass: `(harness, path, content)` for one output file.
- `SyncFilter` — `(harnesses: list[str], flavors: list[TaskFlavor])` pair.
- `resolve_flavor_identity(cfg, flavor) → FlavorIdentity`
- `render_claude(identity, agents_dir) → RenderedDef`
- `render_opencode(identity, agents_dir) → RenderedDef`
- `render_codex(identity, agents_dir) → RenderedDef`
- `sync(cfg, scope, filt, dry_run) → list[RenderedDef]` — the driver; writes on
  `dry_run=False`, always returns the manifest.

Internal modules: `_identity.py` (resolution + classification), `_render.py`
(renderers + `sync` driver). `pyyaml` renders YAML frontmatter (CC + opencode);
`tomli_w` renders Codex TOML — both were already direct deps.

## CLI surface

`src/milknado/cli_config.py` defines `config_app = typer.Typer(name="config")`
wired via `app.add_typer(config_app)` in `cli.py:52`.

```
milknado config sync [--scope project|global] [--harness <csv>] [--flavor <csv>] [--dry-run]
```

- `--scope project` (default): reads `./milknado.toml`, writes to `./.claude/agents/` etc.
- `--scope global`: reads `~/.config/milknado/milknado.toml`, writes to `~/.claude/agents/` etc.
- `--harness` (default: `claude,opencode,codex`): which harnesses to emit.
- `--flavor` (default: all 5): subset of `implement`, `spec`, `spike`, `prototype`, `research`.
- `--dry-run`: prints manifest, writes nothing.

Every generated file begins with `# GENERATED by milknado config sync — do not edit`
(or the TOML-comment equivalent). The tool only ever writes `milknado-worker-<flavor>.*`
— it never touches user files.

After a non-dry-run write, the CLI prints reconnect hints: CC users need a session
restart or `/agents`; MCP clients need `/mcp` reconnect. Def discovery is
session-start only — mid-session disk writes are not picked up automatically.

## Gotcha: `agent_type` must be set in milknado.toml

`config sync` generates the def files but does NOT auto-write `agent_type` into
milknado.toml's flavor tables. Until
`agent_type = "milknado-worker-<flavor>"` is set per `[milknado.flavor.<f>]`
table, `node-runner.js` defaults to `milknado:milknado-worker` and the generated
defs go unused on the native path. See [[history/config-sync-decisions]] ADR-001
follow-up for the recommended fix.
